# 燃香赐福页面 · 文字版设计说明

以下是对应你刚看到的那个完整 HTML 页面的文字版说明，方便你直接阅读、转给团队或存档。内容包括：页面结构、每个模块的职责、交互流程、技术实现要点、后端对接约定。

---

## 一、页面定位

燃香赐福是财神DAO生态的**通缩入口**。用户把 $财神DAO 打入 Solana 黑洞地址，永久退出流通，换取连续 365 天、每日 0.688% 的币本位返还，累计返还 251.12%。

与聚宝盆页面最大的区别：
- 聚宝盆是“放进去还能拿回来”，燃香是“烧掉就永远没了”。
- 燃香受**直播间限定 + 个人燃香额度**双重约束，不是随时能烧、想烧多少烧多少。

因此页面的第一优先级不是“算收益”，而是**让用户在按下按钮前彻底明白不可撤回**，同时清楚自己当前有没有额度、能烧多少。

## 三、核心模块详解

### 3.1 活动状态条

- **开放中**：绿色脉冲点 + “本场燃香进行中” + “全周期剩余 3,240,000 枚 · 额满即止”。
- **未开放**：灰色圆点 + “本场暂未开放” + “以直播间公告为准”，右侧保留“规则”入口。
- 这条 strip 放在页面最顶部，因为“能不能燃”是所有后续操作的前提。

### 3.2 个人燃香额度卡

这是本次调整的核心新增模块。

- **有额度时**：
  - 红色大数字显示可用额度（如 `5,000` 枚）。
  - 进度条显示已用比例（已用/总量）。
  - 下方两列：“今日获得 8,000”和“已使用 3,000”。
  - 底部提示“最早批次将于 10-21 14:32 过期”，过期临近时切换为警示色。
  - 右上角“明细”按钮打开额度批次抽屉。

- **无额度时**：
  - 卡片转为虚线边框、去装饰。
  - 显示“暂未获得本场燃香额度”，副文案“额度由直播间运营按轮次发放，请关注直播间公告”。
  - 燃香输入区和底部按钮同步禁用。

**额度明细抽屉**：展示三列汇总（今日获得/已使用/可用）+ 批次列表。每个批次显示轮次、发放时间、有效期、总额、已用/剩余状态。底部附额度规则：按轮次发放、24 小时有效、不可转让、先进先出消耗。

### 3.3 待领取赐福卡

- 复用聚宝盆的收益卡视觉，但数字改为金色渐变。
- 显示待领取数量（枚）。
- 关键新增：**“距领取截止 623 天”** 的红色警示条，因为文档写“建议 24 个月内领取有效，逾期视为放弃”，这是真实风险点。
- “前往领取”按钮打开领取说明抽屉，明确告知用户资产托管在 `lock.jup.ag`，本页不直接发放，需要跳转链上领取。

### 3.4 全周期额度进度

- 进度条显示已燃比例（如 83.8%）。
- 四格数据：已燃烧 / 剩余可燃烧 / 已释放返还 / 剩余返还池。
- 底部闭合验算：“3,240,000 × 251.12% = 8,136,288 枚，额度不会追加”。
- 这块是回应“返还比燃烧还多”质疑的关键模块，让用户自己验证返还池还有余额。

### 3.5 燃香操作区

- **输入单位是“枚”**，不是 USDC。燃香的核心认知是“烧掉多少币”，不是“花了多少钱”。
- 顶部提示条：“可用额度 5,000 枚 · 单地址限额 50,000 枚”。
- MAX 按钮取 `min(可用额度, 单地址限额)`，不取钱包余额，因为额度才是真正的约束。
- 实时预估两列：每日赐福（T+1）、365 天累计。
- 底部一行：净增数量 + “币本位 · 不随价格变化”。
- 输入异常时，底部出现红色警告行，文案随场景变化：
  - 未达最低燃香量 → “最低燃香 100 枚”
  - 超出可用额度 → “可用额度仅剩 X 枚”
  - 未连接钱包 → 按钮文案变为“请先连接钱包”

### 3.6 我的燃香记录

- 每笔记录一张卡片，根据状态渲染不同内容：
  - **pending（确认中）**：蓝色徽章 + 脉冲点，进度条显示 30%，提示“等待链上确认，通常 15–30 秒”。
  - **confirmed（已确认）**：绿色“释放中”徽章，进度条按天数计算，显示“第 X 天 / 365”，下方两列显示已领取/累计应得/待领取。
  - **failed（失败）**：红色失败徽章，进度条归零，提示失败原因。
- 点击卡片打开详情抽屉，展示释放参数、链上签名、锁仓入口链接、数据来源（前端上报/扫描器补录）。

### 3.7 机制说明 + 风险提示

机制说明用列表形式复现文档里的 8 条定义，重点加粗“个人燃香额度由后台按轮次发放”“额度不可转让、不可跨场累积”“燃香即销毁”。

风险提示用编号列表，共 7 条，覆盖不可撤回、额度不可转让、额度刚性、开放时间不确定、领取期限、币本位不保本、非投资建议。

### 3.8 底部固定操作栏

按钮文案随状态动态变化：

| 状态 | 文案 | 是否可点击 |
|---|---|---|
| 未连接钱包 | 请先连接钱包 | 可点击（触发连接） |
| 未开放 | 本场暂未开放 | 禁用 |
| 无额度 | 暂未获得燃香额度 | 禁用 |
| 未输入 | 请输入燃香数量 | 禁用 |
| 低于最低量 | 未达最低燃香量 | 禁用 |
| 超出额度 | 超出可用额度 | 禁用 |
| 正常 | 燃香 X 枚 | 可点击（打开确认抽屉） |

下方辅助文案：“燃烧后永久退出流通，操作前请仔细确认”。

## 四、燃烧确认抽屉（三重确认）

这是全页仪式感最重的一步，因为操作不可逆。

1. **红色警示条**：“本次燃香的 X 枚 $财神DAO 将被转入 Solana 黑洞地址，永久退出流通，不可撤回、不可找回。”
2. **六行摘要**：燃烧数量、消耗额度、燃烧后剩余额度、每日赐福、365 天累计返还、净增。
3. **勾选确认**：用户必须勾选“我已了解该部分 $财神DAO 将永久退出流通，操作不可撤回、不可退款，并确认燃烧数量与额度消耗无误”，按钮才从禁用变为可用。
4. **按钮文案**：“确认燃烧 X 枚”，不是笼统的“确认”。

## 五、钱包连接与交易发送流程

### 5.1 钱包连接

- 支持 Phantom 和 Solflare。
- 页面加载时尝试以 `onlyIfTrusted` 方式静默恢复上次连接，不主动弹窗。
- 用户点击顶栏钱包芯片即可连接；已连接时芯片变绿、显示缩略地址，点击芯片复制完整地址。
- 监听 `accountChanged` 和 `disconnect` 事件，切换账户或断开时自动刷新记录列表。

### 5.2 交易构造

- Solana Web3.js 和 SPL Token SDK 采用**动态 import**，不阻塞首屏。
- 构造标准 SPL Token transfer 指令：从用户 ATA 转 $财神DAO 到黑洞 ATA。
- 发送前检查黑洞 ATA 是否存在，不存在则明确报错，避免交易在链上失败浪费 gas。
- 签名后等待链上确认，60 秒超时保护。

### 5.3 三写流程（核心）

```
用户点击确认燃烧
      │
      ▼
发送交易 → 拿到 txHash
      │
      ├──► 【写1】POST /api/burn/submit  { txHash, wallet, amount }
      │         → 后端落 pending 记录
      │         → 前端乐观显示“确认中”
      │         → localStorage 缓存 txHash
      │
      ▼
等待链上确认（confirmTransaction）
      │
      ├──► 【写2】POST /api/burn/confirm { txHash, wallet }
      │         → 后端用 txHash 拉链上真实数据
      │         → 校验燃烧数量 / 黑洞地址 / 发起钱包
      │         → 更新 status = confirmed
      │         → 解析锁仓地址 / 生成 lock.jup.ag 专属链接
      │
      ▼
清缓存 → 扣减本地额度 → 刷新记录列表 → Toast“燃香成功”
```

**兜底**：后端定时任务扫描黑洞地址转入记录，补录前端没上报的（用户关页面、网络断）。

**pending 恢复**：页面加载时检查 localStorage 中是否有未完成的 txHash，有则自动调 `/api/burn/confirm` 尝试恢复，避免用户关掉页面就丢单。

## 六、后端接口约定

真实后端需要实现以下接口：

| 方法 | 路径 | 请求体 | 职责 |
|---|---|---|---|
| POST | `/api/burn/submit` | `{ txHash, wallet, amount }` | 乐观写，落 pending 记录，幂等（同一 txHash 不重复写） |
| POST | `/api/burn/confirm` | `{ txHash, wallet }` | 链上校验 + 确认写，返回完整记录 |
| GET | `/api/burn/list?wallet=xxx` | — | 返回该钱包所有燃香记录 |
| GET | `/api/burn/:txHash` | — | 返回单笔状态，用于 pending 恢复 |

**后端 `confirm` 接口必须做五件事**：
1. `getParsedTransaction(txHash)` 查交易。
2. 校验 `tx.meta.err` 为空。
3. 校验确实转入了黑洞地址。
4. 校验数量与前端声明一致。
5. 校验发起钱包与用户一致。

验证通过再更新记录，防止前端被篡改。

## 七、数据库表设计建议

```sql
CREATE TABLE burn_records (
  id              BIGSERIAL PRIMARY KEY,
  wallet_address  VARCHAR(44) NOT NULL,
  tx_hash         VARCHAR(88) NOT NULL UNIQUE,
  burn_amount     NUMERIC(20, 6) NOT NULL,
  lock_address    VARCHAR(44),
  lock_url        TEXT,
  slot            BIGINT,
  block_time      TIMESTAMPTZ,
  status          VARCHAR(16) NOT NULL,  -- pending / confirmed / failed
  source          VARCHAR(16) NOT NULL,  -- frontend / scanner
  raw_tx          JSONB,
  created_at      TIMESTAMPTZ DEFAULT now(),
  confirmed_at    TIMESTAMPTZ
);
```

关键点：
- `tx_hash` 加 UNIQUE 约束，天然去重。
- `block_time` 用链上时间，不用客户端时间。
- `raw_tx` 存完整回执，备查。
- `source` 区分来源，方便排查。

## 八、关于 lock.jup.ag 数据的获取

你提到“每一笔燃烧赐福对应一个 lock.jup.ag 专属链接”，但前端需要展示“已领取/待领取”等实时状态。

**三条路径**：

1. **第三方索引 API（推荐）**：用代币 mint 地址查询该代币下所有锁仓合约的解析数据，返回字段包含 `withdrawn`（已领取）、`claimable`（可领取）、`next_unlock`（下次解锁时间）。后端拿这些数据与自己的锁仓地址映射匹配。
2. **自建链上查询**：从专属链接中提取锁仓账户地址，用 Solana RPC 的 `getAccountInfo` 读取原始账户数据，按 Jupiter Lock 程序定义的账户结构解码。开发量大但完全自主。
3. **模拟前端请求（不推荐生产）**：观察 lock.jup.ag 前端的 Network 请求，但接口不稳定、可能被限流。

**落地建议**：先确认专属链接是否包含锁仓账户地址，把这个地址存进 `burn_records.lock_address`，然后选方案一或方案二。

## 九、与现有代码的关系

当前 HTML 中的 `MockBackend` 用内存 Map + localStorage 模拟后端，但方法签名已按真实接口设计好：

- `submit()` → 对应 `POST /api/burn/submit`
- `confirm()` → 对应 `POST /api/burn/confirm`
- `list()` → 对应 `GET /api/burn/list`
- `get()` → 对应 `GET /api/burn/:txHash`
- `fail()` → 标记失败

接入真实后端时，只替换这五个方法体为 `fetch` 调用，前端其余逻辑（渲染、交互、状态判断）不需要动。

`Quota` 对象中的额度数据（total/used/batches）也应改为从后端接口获取，前端只负责渲染。

## 十、需要你确认或补充的事项

1. **黑洞 ATA 是否已初始化**：SPL Token 转账要求目标 ATA 存在，项目方需提前创建黑洞地址的 $财神DAO ATA，否则交易会失败。
2. **锁仓地址从哪来**：确认 `lock.jup.ag` 专属链接的格式，以及锁仓是用户燃香时同时创建，还是项目方批量创建后另行提供。
3. **额度数据来源**：个人燃香额度由后台按轮次发放，前端需要调哪个接口获取？批次列表是否也由后端返回？
4. **RPC 节点**：建议使用自己的 RPC 节点（Helius / QuickNode / Triton），公共 RPC 有频率限制，不适合生产。
5. **后端扫描兜底**：建议增加定时任务扫描黑洞地址转入记录，补录前端漏报的订单。

以下是 **“社区 SDK + 索引 API（以 MadeOnSol 为例）”** 的文字版方案。核心思路是**读写分离**：用 MadeOnSol 解决“查得到”的问题，用社区 SDK 解决“领得了”的问题，用户在 DApp 内完成从查看数据到领取的全部操作，无需跳转 `lock.jup.ag`。

## 一、整体架构：读用 MadeOnSol，写用社区 SDK

```
┌─────────────────────────────────────────────────────┐
│                      前端 DApp                        │
│  展示 claimable / next_unlock   │  点击「领取」按钮     │
└───────────────┬───────────────────────┬──────────────┘
                │                       │
                ▼                       ▼
┌───────────────────────────┐ ┌─────────────────────────┐
│      你的后端              │ │      你的后端            │
│  调 MadeOnSol token_locks │ │  调社区 SDK              │
│  拿 claimable/next_unlock │ │  构造 withdraw 指令      │
│  → 缓存 → 匹配用户数据     │ │  → 返回给前端签名发送     │
└───────────────┬───────────┘ └───────────┬─────────────┘
                │                         │
                ▼                         ▼
        MadeOnSol API               Solana RPC
        （索引聚合层）              （Jupiter Lock 程序）
```

**关键结论**：MadeOnSol 负责**读**（查询派生数据），社区 SDK 负责**写**（构造领取交易）。两者不重叠、不冲突，配合使用才能在不跳转外部页面的前提下，提供完整的“查看—领取”体验。

## 二、读：用 MadeOnSol 获取 `claimable` 和 `next_unlock`

### 2.1 调用方式

MadeOnSol 提供了官方的 **TypeScript SDK（`madeonsol`）**，可以直接在后端 Node.js 环境使用：

```bash
npm install madeonsol
```

```javascript
import { MadeOnSolREST } from "madeonsol";

const client = new MadeOnSolREST({ apiKey: process.env.MADEONSOL_API_KEY });

// 按 mint 地址聚合查询该代币下所有锁仓合约
const res = await client.token.locks("你的财神DAO代币Mint地址", {
  program: "jupiter-lock"  // 只查 Jupiter Lock 的锁仓
});

// res.data 中包含每笔锁仓的完整派生视图
```

### 2.2 返回的关键字段

`token_locks` 返回的每一条锁仓记录，都包含你需要的所有派生字段：

| 字段 | 含义 | 前端用途 |
|:---|:---|:---|
| **`claimable`** | 当前可领取数量 | 展示“待领取 X 枚” |
| **`next_unlock`** | 下次解锁时间 | 展示“下次释放：2026-11-01” |
| **`withdrawn`** | 已领取数量 | 展示“已领取 X 枚” |
| **`unlocked`** | 已解锁数量 | 计算进度条 |
| **`locked_raw`** | 当前仍锁定的数量 | 展示剩余锁定 |
| **`LockStatus`** | 锁仓状态（活跃/已完成等） | 状态徽章 |
| **`seconds_until_next_unlock`** | 距离下次解锁的秒数 | 倒计时展示 |

此外，返回结果还包含一个 **`summary`** 汇总对象，内含 `lock_count`（锁仓总数）、`nearest_next_unlock`（最近的下次解锁时间）等聚合信息。

### 2.3 后端缓存策略（50 用户场景的关键）

`token_locks` 是**按 mint 聚合查询**，一次调用返回该代币下**所有**锁仓合约，而不是每个用户单独调一次。因此：

- **后端调用一次** → 拿到全量锁仓列表 → 在本地用“用户钱包 ↔ 锁仓地址”映射匹配出当前用户的数据。
- **缓存 5–10 分钟**：50 个用户共享同一份缓存结果，日调用量大约在 **20–150 次**之间，完全在 MadeOnSol 免费层的 **200 次/天**额度之内。

**不要做的事**：前端直连 MadeOnSol、无缓存、每次刷新都实时查询。这种设计会让 50 个用户轻松打满 200 次额度。

## 三、写：用社区 SDK 构造 `withdraw` 指令

### 3.1 SDK 选择

社区维护的 **`ChiefWoods/jupiter-sdk`** 是一个 Codama 生成的链上程序 SDK，包含 `lock` 产品，支持三种客户端形态：

| 形态 | 导入路径 | 适用场景 |
|:---|:---|:---|
| **web3js** | `jupiter-sdk/lock/web3js` | 配合 `@solana/web3.js` v3 使用 |
| **kit** | `jupiter-sdk/lock/kit` | 配合 `@solana/kit` 使用 |
| **rust** | `jupiter-program-sdk` with `lock` feature | Rust 后端 / CPI |

对于大多数 DApp 前端，**`web3js` 形态**是最直接的选择。

### 3.2 构造领取指令

Codama 生成的 SDK 会根据 IDL 自动生成指令构造函数。`lock` 产品的领取指令通常命名为 `createWithdrawInstruction`（或类似的 `getWithdrawInstructionAsync`，取决于 SDK 版本）。

```javascript
import { createWithdrawInstruction, LOCK_PROGRAM_ID } 
  from "jupiter-sdk/lock/web3js";
import { Transaction } from "@solana/web3.js";

// 从 MadeOnSol 数据中拿到该用户的锁仓账户地址
const lockAccount = userLock.lockAddress;

const instruction = await createWithdrawInstruction({
  // 账户参数：锁仓账户、接收者钱包、代币账户等
  // 具体参数名以 SDK 生成的类型定义为准
  lock: lockAccount,
  recipient: userWallet,
  // ... 其他必要账户
});

const tx = new Transaction().add(instruction);
// 让用户钱包签名并发送
```

> **注意**：`withdraw` 指令所需的具体账户参数，会因 Jupiter Lock 程序的版本而异。建议在 Devnet 上先用 SDK 测试，确认参数结构无误后再上主网。SDK 的 README 中明确说明它是 **社区独立维护、非官方包**，因此锁定一个经过验证的 SDK 版本并固定依赖，是必要的工程实践。

### 3.3 领取的本质

Jupiter Lock 的官方 FAQ 确认：**解锁的代币不会自动发送，接收者必须手动触发一笔 claim 交易**才能将代币从托管账户转入自己的钱包。`lock.jup.ag` 只是一个前端界面，链上真正执行的是 Jupiter Lock 程序的 `withdraw` 指令。你的 DApp 只要构造并发送这笔指令，用户就完成了领取，**完全不需要离开你的页面**。

## 四、完整流程：从查看到领取

```
1. 用户打开燃香页
   → 后端调 MadeOnSol token_locks($财神DAO mint)（有缓存则读缓存）
   → 匹配出当前用户的锁仓数据
   → 前端展示 claimable、next_unlock、withdrawn、释放进度

2. 用户点击「领取」
   → 前端从后端拿到该用户的锁仓账户地址（lockAddress）
   → 调社区 SDK createWithdrawInstruction 构造 withdraw 交易
   → 钱包弹出签名 → 用户确认
   → 交易发送 → 等待链上确认

3. 确认成功后
   → 前端刷新 → 后端重新调 token_locks（或等待缓存过期）
   → claimable 减少、withdrawn 增加
   → 前端更新展示
```

**领取动作本身不消耗 MadeOnSol 的 API 额度**，因为它走的是 Solana RPC + 社区 SDK，不经过 MadeOnSol。

## 六、需要提前确认的两件事

1. **锁仓账户地址是否可得**：你的后台必须保存每一笔燃香对应的 **锁仓账户地址（Lock Account Address）**，而不只是 `lock.jup.ag` 的页面 URL。这是构造 `withdraw` 指令和匹配 MadeOnSol 数据的共同前提。

2. **SDK 版本的指令参数**：`createWithdrawInstruction` 的具体账户参数名和结构，以你所使用的 `jupiter-sdk` 版本生成的 TypeScript 类型为准。建议在 Devnet 上完成一次完整的“查询 → 构造 → 签名 → 确认”闭环测试，再切换到主网。

## 七、总结

**MadeOnSol 解决“查”，社区 SDK 解决“领”，你的后端做“缓存 + 匹配”，前端做“展示 + 签名”。** 四层各司其职，用户全程不跳转 `lock.jup.ag`，50 用户场景下免费层足够支撑，唯一需要提前锁定的是**锁仓账户地址**和**SDK 的指令参数结构**。
